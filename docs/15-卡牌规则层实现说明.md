## 2. R45：`docs/.gdignore` 与运行时数据的冲突（本轮新诊断）

第 15 轮 R39 给 `docs/` 加了空 `.gdignore`，避免 Godot 把设计 CSV 当成翻译表导入。这个处置是对的，但有个未声明的副作用：

- `.gdignore` 让编辑器**跳过整目录扫描**，导出时该目录不进包；
- 本轮 headless 实测：`res://docs/buff-card-library.json` 在**工程内**仍可读（`.gdignore` 只挡扫描，不删文件），所以编辑器里跑不会报错；
- 但**导出的独立 app 里读不到**——这属于「F5 能跑、打包就崩」的典型隐患。

处置：设计源仍**唯一保留**在 `docs/buff-card-library.json`（策划不二改），另由 `tools/build_card_runtime_data.py` 生成 `data/buff-card-library.json`，运行时只读 `data/`。脚本带 `--check` 模式做规范化 JSON 指纹比对，是二者之间唯一的、可复跑的一致性闸门；报告见 `docs/card-runtime-data-report.json`。headless 断言里也做了两副本的语义一致性比对。

> 结论口径：`.gdignore` 只挡扫描，不挡工程内 `FileAccess`；但导出后不可用，故运行时数据**不得**放 `docs/`。

## 3. 三个「实现解释」，不是新拍板

`11` §6 的文字规则有需要落地才能发现口径歧义的地方，本轮按下表实现，逐条可被复核，若用户判断不同可直接改 `CardDeck.gd` 重跑验证脚本：

| 歧义 | 实现口径 | 理由 |
|---|---|---|
| 「本局已选卡不再进入候选」与「堆满 `stack` 上限的卡也移出池」并列 | **已选且 `stack` 未满的卡仍可再出现**（这就是堆叠）；`stack=1` 等价于选过即移出 | 若按字面「选过就不再出现」，`stack` 字段（49 张为 1、其余 2–4）将完全失效 |
| `affix_wuxiang` 压 2 选 1、`card_wuxiangpo` 恢复 3 张 | 已选无相破时无条件恢复 3 张，优先级高于词缀压缩 | `card_wuxiangpo` 的 `req` 本身要求无相词缀，不存在「没有无相却恢复」的分支 |
| 玩家 `defense_rate` 是否进伤害峰值 | **不进**。`peak_damage()` 取「目标不减伤」的最坏口径 | 玩家变肉属生存维度，混进峰值会把「伤害变低」误当成「红线没被突破」，是掩盖而非守住红线 |

首轮 headless 实测确实抓到过一次这个误算（全卡叠加峰值被算成 3437），已改为最坏口径后复跑为 **3996**。

## 4. 落地了什么、没落地什么

**已落地**（`scripts/CardDeck.gd`）：

- `hash(run_id, stage)` 用自实现 **FNV-1a 32 位**，不依赖引擎内置 `hash()`，跨版本可复算；`runA:1 = 4264777024`，Python 侧可独立核对。
- 加权无放回抽样：卡库 `weight`（凡品 10 / 灵品 5 / 仙品 2 / 劫品 3），仙品按层数线性 `×(1+0.1×stage)`；**同类同层最多 1 张**。
- 过滤链：`stack` 上限 → `req`（`school:` / `skill:` / `gear:` / `affix:` / `stage>=`）→ `unlock`（`realm:N`）→ `excl[]` **双向**互斥。未知前置一律不放行，宁可少给卡也不静默破坏规则。
- 联动：无相压 2 选 1、无相破恢复 3 张、`card_sheli` / `card_wuxin` 封牌后 `offer()` 恒空、`card_shouzhuo` 主动舍牌、第 9 层 Boss 后不弹。
- 五上界运行时守卫：触碰上界变量的卡必须显式带 `pool` 或 `cap` 声明（R32 机器规则的运行时版），`pool:offense_pool` 的增益并入共享 600 点池而非直接叠 `base`；`peak_damage()` 逐项钳回 `base≤180 / realm≤1.60 / pool≤600 / combo≤2.5 / crit≤1.8`。
- `pick_event` 返回 `11` §5 的增补字段（`card_id` / `card_rarity` / `card_category` / `seen_before`）及 `run_id` / `seed`，便于 M6 埋点复现；**未写盘、未联网**，落地仍归 DF-22 的本地埋点工程范围。

**未落地（不要误读成已完成）**：

- 卡牌效果**只实现触碰五个上界变量的 9 张卡**的数值部分；其余 `RunState.*` / `VfxLayer.*` / `signal.*` / `MetaSave.*` / `UI.pick_event` 钩子留给正式战斗工程按 `01` §12 节点树接入。
- **没有 UI**、没有场景、没有把规则层挂进 `MinimalRun.tscn`；`assets/ui/cards/` 的 10 张卡面与 `buff-card-preview.html` 仍是独立预览，未与本脚本连线。
- **不是游戏**，也不是 GUI 画面验证；像素硬边、镜像、480×270×4 对齐、R22 阴兵对比度仍需用户按 F5 目检。
- R33（6 s / 12 s 读卡窗口）、R34（`combo_hash` 区分度）、R35（夺主改 `k` 后重算 `B`）、72 卡权重与概率**全部仍待实测 / 未拍板**，本轮不改 `B` / `V` 公式与结论。

## 5. 验证证据（都是离线 / headless，不是 GUI）

```
python3 tools/build_card_runtime_data.py --check
Godot --headless --path . --script res://tools/verify_card_rules.gd
python3 tools/check_traceability.py
python3 tools/verify_damage_ceiling.py
python3 tools/final_selfcheck.py
```

`tools/verify_card_rules.gd` 由 4.7.2 引擎自己编译 `CardDeck.gd` 并跑 **23 项断言**，结果写 `docs/card-rules-report.json`：

- 卡库 72 张 / 两副本语义一致 / `.gdignore` 探针；
- FNV-1a 跨实现可复算、同 `(run_id, stage)` 候选恒定、不同 `run_id` 序列确实不同；
- 1–8 层各弹一次、第 9 层不弹、同类最多 1 张、一局恰好 8 次选择（按总次数，堆叠可重复选同一张）；
- 无相 / 无相破、双向互斥、堆叠上限、`realm:6` 解锁与 `stage>=5` 前置、封牌；
- **72 张卡逐张 + 全卡叠加**：违规 0、峰值 **3996 < 4400**、守卫事件 105 条（证明不是空跑恒等式）；
- `pick_event` 字段齐全。

首轮跑出过 2 项 FAIL（「8 次选择」按不同 ID 数断言、「伤害峰值混入玩家减伤」），均已按 §3 口径修正后复跑 **23/23 PASS**。这两条如实保留在本文，不抹掉。

> **口径差异（别误读成矛盾）**：`verify_damage_ceiling.py` 报「触碰上界卡 **8 张**」，而 `CardDeck.UPPER_KEYS` 逐卡守卫扫描覆盖 **9 张**——多出的一张是 `defense_rate`（玩家减伤，属生存侧，clamp 到 0.75）。前者只统计 5 个**攻击**上界变量，后者把生存侧变量也纳入守卫。两者违规数同为 **0**、守规则峰值同为 **3996**，结论一致。
