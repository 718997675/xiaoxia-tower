## 1. 先纠一个歧义：这不是「新加一套系统」，是给已有机制填内容

`02` §4 P0-1 早已写下「技能池 8、每局选 4、**层间可换 1 个**」，`02` P1-4 写下「**层间三选一** 10 s → 6 s」，`02` §5 的 M6 埋点里甚至已经有 `pick_event { stage, offered[], picked, dps_delta_est }`。也就是说：**三选一的壳一直在，缺的是卡片内容**。

所以本轮的正确做法不是再叠一层「Buff 系统」，而是把**已有的层间三选一**具体化成 72 张可选卡，并把 `pick_event` 补齐字段。这样做有三个好处：

1. 不新增核心循环节点、不新增场景流、不动 `01` §5 的 9 层结构；
2. 直接兑现 P0-1「构筑空间收益最大、成本最低」这条最高优先级调整；
3. 72 张卡的**实现钩子全部落在已有字段/信号上**（见 §5），不需要新架构。

> **「每次过一个塔」的口径**：字面可能是「每通关一座塔（一局）」，但那样一局只选 1 张，与「够肝 / 30 h」目标和 StS「每场战斗后选牌」的节奏都不符。本稿默认 **每通过 1 层**（`stage_cleared` 后）弹一次，9 层塔共 **8 次**（第 9 层 Boss 后改为传承结算，不弹）。若你本意是「每局一次」，请指出——那会大幅削弱本系统的作用，需要重算 §6 的有效局数。

## 2. 与 Slay the Spire 的对应关系（只借结构，不照搬内容）

| StS | 本项目 | 差异 |
|---|---|---|
| 每场战斗后 3 选 1 | 每层通关后 3 选 1 | 本项目是**即时横版战斗**，卡牌在层间选、不进战斗手牌 |
| 牌库 / 抽牌堆 / 弃牌堆 | **单局卡池 + 已选卡列表** | 没有「打出卡牌」，卡是**永久被动**，选了就生效到本局结束 |
| Common / Uncommon / Rare / Curse | 凡品 / 灵品 / 仙品 / **劫品** | 4 档，全部落在 24 色板的 4 段色内，不新增色相 |
| 遗物 / 药水 / 升级 | 装备 3 槽 / 传承灵韵 / 层间铸器 | 已有机制，卡牌只与它们**联动**，不替代 |
| 每局从零构筑 | 每局从零构筑 + **局外 1 条灵韵继承** | Roguelite，不是纯 Roguelike |

**关键取舍**：不做「战斗中打牌」。理由是 `01` §5 已定「横版即时战斗 + 每次释放技能有特效」，如果战斗中再插打牌，会和 `SkillCaster.gd` 的 `cast_lock` 与 4 信号时序打架，也违背用户「PK 是横版」的原始诉求。卡牌做成**层间永久被动**，既保留 StS 的构筑快感，又不改战斗手感。

## 3. 卡池：72 张 / 6 类 × 12 张

| 键 | 类别 | 设计职责 | 纯数值张数 | 与其他系统的咬合 |
|---|---|---|---|---|
| `dmg` | 技能伤害 | 改技能的命中数 / 落点 / 条件 / 转化 | 3 | 8 技能形状语言（`06` §4）、`SkillCaster.gd` |
| `attr` | 属性提升 | 传统数值成长，但**受红线约束** | 10 | `01` §8.1 四个上界 |
| `mech` | 机制改变 | 改规则、时序、信息、技能槽 | 0 | 12 词缀、3 槽、道途目标、M3 传承 |
| `res` | 资源灵力 | 灵力 / 冷却 / 灵石经济 | 1 | `spirit_max`、经济三件套 |
| `surv` | 生存回复 | 生命 / 护盾 / 无敌窗口 / 替身 | 3 | 回春诀、纸傀儡、金刚罩 |
| `syn` | 构筑风险 | 4 流派联动 + 高代价高收益 | 0 | 4 流派标签、天劫词缀、道行倍率 |
| **合计** | **72 张（≥64 达标，余量 8 张给二期）** | | **17 / 72 = 23.6%** | |

**沿用 `02` P0-2 的硬约束**：纯数值卡 ≤ 1/3。这里 23.6%，达标。理由不是「凑数字」，而是 `02` §2 的 D3 反面案例——只缩放数值会让高层失去决策；`02` R8 也明确「解锁链不能全是数值」。所以 55 张是 `hybrid` / `mechanical`，其中 `mechanical` 占 34 张。

**稀有度分布**：凡品 30 / 灵品 30 / 仙品 8 / 劫品 4。劫品是「有代价的强卡」（如 `card_wugen` 灵力上限 −20% 换 CD −12%），是 StS 的 Curse 思路但**不做成纯负面**，避免玩家觉得被惩罚。

**解锁**：多数 `unlock=none`；8 张仙品挂 `realm:3` 或 `realm:6`（金丹 / 炼虚），让境界解锁链（P0-3 的 27→45–60 钩子）多一批**非数值**内容，正好补 `02` R8 的缺口。全部数值待实测。

## 4. ⚠️ 最重要的一条：卡牌不能把数值红线再撞回来

`02` §4 P0-3 把 `realm_ratio` 从 4.00 压到 1.60 后，全最大伤害：

| 口径 | 算式 | 结果 | 与第 9 层 Boss 血量 4400 |
|---|---|---|---|
| v0.1 全最大（红线） | `(180×4.00+600)×2.5×1.8` | **5940** | ❌ 一击清层 |
| v0.2 全最大（Q11 已接受） | `(180×1.60+600)×2.5×1.8` | **3996** | ✅ 约需 2 次命中 |
| 余量 | `4400 − 3996` | **404 点** | 只剩 9.2% |

**任何「伤害 ×1.35」式的卡牌倍率都会让 3996 → 5394，红线当场复燃。** 因此本系统定下一条不可协商的实现铁律：

> **卡牌不得提高 `compute_damage` 的五个上界：`realm_ratio ≤ 1.60`、`extra_pool ≤ 600`、`combo_multiplier ≤ 2.5`、`crit_multiplier ≤ 1.8`、`base ≤ 180`。**
>
> **第 15 轮修订（R32 已处置）**：原「四上界铁律」漏了第五变量 `base`。3 张 `base_damage` 卡直接叠加会把 `base` 推到 236（峰值 **4399**，距 4400 只剩 1 点）；若连已声明 `pool` 的卡也被实现成直接叠加则 `base=254` → **4529，红线击穿**。已给 `card_jianfeng / card_danbao / card_shuangren` 补齐 `pool:offense_pool` + `cap:600`，并把「凡触碰上界变量的卡必须显式带 `pool` 或 `cap`」写成机器核对规则。复算 **PASS**：`tools/verify_damage_ceiling.py` → `docs/damage-ceiling-report.json`（违规 0、守规则峰值 3996 < 4400）。
> 伤害类卡只允许做两件事之一：
> ① 改**达到上界的路径**（命中数、落点分配、贯穿、命中条件、CD、施法时序）——单次峰值不变；
> ② 把增益并入 `offense_pool`，且 `offense_pool` 与 `extra_pool` **共享同一个 600 点上限**（不是另开一个池）。

这条铁律已经写进 `buff-card-library.json → offenseCeiling`，并由 `build_buff_cards.py` 在生成时核对所有 `params` 里是否出现越界声明。例如 `card_poyun`（飞剑分裂 2 道 ×0.6）、`card_leizhuan`（落点 +1 但总伤均分）、`card_shouyin`（3 层引爆按 3 次均值）都是「改路径不改峰值」的样板；`card_huixin`（暴击倍率 +0.15 但 `cap:1.8`）、`card_kongzhan`（`cap:2.5`）则是显式带上界的样板。

**仍待做**：卡牌全部生效后的 8.1 极值验算**本轮未重跑**，标待实测；`docs/SkillCaster.gd` 里的 `clampi(..., 1, 9999)` 是最后兜底，但不是设计解法。验收时必须补一条「第 9 层 Boss 战仍需 ≥2 次命中」。

## 5. 实现钩子（不改架构，全部落在已有字段/信号）

`docs/SkillCaster.gd` 现有的 4 个信号与 `compute_damage()` 字段就是卡牌的落点：

| 钩子 | 对应字段 / 信号 | 被哪些卡用 |
|---|---|---|
| `SkillCaster.base_damage` / `extra_pool` / `combo_multiplier` / `crit_multiplier` / `defense_rate` | `compute_damage()` 的 5 个输入 | `dmg` / `attr` / `surv` 共 26 张 |
| `VfxLayer.vfx_requested` | 已有异步特效信号 | 分裂 / 落点 / 贯穿 / 追加段数 8 张 |
| `signal.damage_applied` | 已有伤害结算信号 | 叠层 / 引爆 / 转化 8 张 |
| `RunState.*` | 灵力、生命、护盾、CD、技能槽、词缀上限、经济、可见性 | 其余多数 |
| `MetaSave.legacy_effects` | Q26 方案 B 新增字段（见 `10` §4） | `card_lunhui` 1 张 |
| `UI.pick_event` | `02` §5 已有埋点 | 抽卡规则类 7 张 |

**`pick_event` 字段增补**（不推翻 `02` §5，只追加）：
```
pick_event { stage, offered[], picked, dps_delta_est,
             card_id, card_rarity, card_category, seen_before }   ← 后 4 个为本轮新增
```
`seen_before` 用来验证 §6 的 R33「新卡阅读时间」是否需要放宽。

## 6. 抽取规则、堆叠、互斥

| 项 | 规则 |
|---|---|
| 触发 | `stage_cleared` 后，第 1–8 层各一次；第 9 层 Boss 后不弹 |
| 候选 | 3 张，**同类最多 1 张**，`hash(run_id, stage)` 确定性种子（便于埋点复现 / 存档回放） |
| 去重 | 本局已选卡不再进候选；堆满 `stack` 上限的卡也移出池 |
| 权重 | 凡品 10 / 灵品 5 / 仙品 2 / 劫品 3；层数越高，仙品权重线性 ×(1 + 0.1×层数)，**待实测** |
| 前置 | `req` 未满足的卡不进候选（如 `card_jianyi` 需剑修流派、`card_wuxiangpo` 需「无相」词缀） |
| 互斥 | `excl[]` 双向生效：已选 A 则 B 不再出现，反之亦然（如 `card_nianzhuan` ↔ `card_juling`、`card_sheli` ↔ `card_zhuansheng`） |
| 联动词缀 | `affix_wuxiang`（无相）把 3 选 1 压成 2 选 1；`card_wuxiangpo` 可恢复 3 张 —— **这是卡牌与 12 词缀的反向咬合**，也是 `02` R7「词缀不该只收窄 build」的一个反例 |
| 舍牌 | 默认不开放（StS 的 skip 在这里做成一张卡 `card_shouzhuo`：主动放弃本层抽卡换后续减伤） |
| 停止抽卡 | `card_sheli` / `card_wuxin` 会令本局后续不再弹卡，UI 必须显示「本局已封牌」，避免玩家以为卡了 bug |

### 与耐玩性模型的关系（诚实标注）

`02` §3 的 `B = F × C(S,k) × Q`、`V = η × B × O × A` **没有卡牌维度**。加入卡牌后，单局多了 8 次有序选择，朴素上界是 `3^8 = 6561` 条选择序列，但这**只是数学上界**：

- 受「同类最多 1 张 / 已选去重 / 前置 / 互斥 / 解锁」约束，实际可达序列远小于 6561；
- `η = 0.10` 的「可行且体验显著不同」折扣会把大部分序列吃掉——72 张卡里若玩家每局都只挑 `+3% 暴击` 这类无感卡，构筑差异就是 0；
- 因此**本轮不改 `B` / `V` 的公式与结论**，只把卡牌记作「提高决策密度的一个新增因子」，并新增一条 M6 检查（见 §8）。等内测埋点有 `combo_hash` 与 `pick_event` 数据后再校准，才允许把卡牌写进公式。**这是设计纪律，不是保守。**

## 9. 边界（不要误读）

- 用户确认的是「**要做这套系统**」，不是「确认 72 张卡的每条数值」。全部数值、权重、阈值、时长窗口标 **待实测**。
- `01`–`09` 正文**均未原位修改**；`01` §15 补 M6、`01` §4 假设修订（R29/R30）、M3 的 `legacy_effects`（R27）统一以 `docs/10` 的**改前/改后对照**给出，等用户整体确认策划案后才合并 v0.2。
- **Q1 仍未填**（本机 Godot 小版本），硬门禁 3/4，未建工程、未产出 `design-freeze.json`、`design-freeze-draft.json` 仍 `frozen=false`。
- 本轮**0 张源图 / 0 积分**：72 张卡、卡框、纹样、预览页全部程序化生成；R9 字体最终核验、Godot 编辑器验证、4× 实机排版、M4 贴图预算复核仍待做。
- 卡池是**内容量最小的耐玩性杠杆**：不加关卡、不加敌人、不加职业（Q20 仍是 1 职业），但 72 张卡的实现成本主要在 `RunState` 字段与 UI，不在美术。
